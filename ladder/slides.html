評価制度の例

エンジニアの評価基準
5軸 × 5段階

採用・育成・評価に、1つの基準を使う
  • 何を測るか　上流・型の運用・ドメイン・検証・基盤の5軸
  • どう区切るか　依頼元に対して、どこまで一人で任せられるかの5段階
  • 何で判定するか　リポジトリの成果物と、型を回した記録
  • 何に使うか　現在地の評価、次に伸ばす1軸、候補者の見極め

評価・育成・採用に、同じ5軸を使う

3つを別々の制度にしない。軸と段階は共通で、材料だけが替わる
評価いまどこにいるか
材料
リポジトリの成果物と、型を回した記録
結果
5軸それぞれの点と、A と B の低いほうで決める段階。証拠が無い軸は「未観測」
育成次に何を伸ばすか
材料
評価で付いた5軸の段階
結果
最も低い1軸と、それに対応する手順。回した成果物が次の評価の材料になる
採用誰を取るか
材料
面接と課題。前職の成果物は持ち込ませない
結果
在籍者と同じ5軸の段階。B は入社前に測れないので見込みで置き、入社後に採点し直す
同じ基準だから比べられる
在籍者と候補者が同じ5軸の上に並ぶので、いまのチームに足りない軸を、育てるか取るかで埋められる。制度を別々に持つと、換算表と食い違いの調整が残る。

評価の軸：5軸

態度ではなく、成果物で確かめられるものだけを軸にする
軸測るもの
A上流・提案と関係者調整要件を引き出し、完了条件と非機能を定める。依頼元と社内の非開発者に対する説明と調整
B標準化されたワークフローの運用配られた型の運用。回せる、選べる、直せる
Cドメイン理解依頼元の業務と現行システムの把握、および関係者間での共有
D検証・品質保証何を確かめれば正しいと言えるかの設計
Eインフラ・基盤環境とパイプラインの構築、構成の選定とリポジトリ全体の管理
B が、エージェントで開発を回すチームに固有の軸
生成そのものの巧拙ではなく、配られた型に乗れるかを測る。他の4軸は既存の公開ラダーと重なる。
推進力・当事者意識のような態度の軸を持たない
進捗管理と期待値調整は A、型の規律と仕組みへの反映は B に収まり、独立の軸として残る中身が無い。

段階：L1〜L5

尺度は「依頼元に対して、どこまで一人で任せられるか」
Lv委任範囲
L1標準化の外。単位作業を指示され、成果物はレビューで書き直される
L2標準化されたワークフローを理解し、単位作業をレビュー前提でやり切る
L3担当領域を自走する
L4案件の一領域を依頼元との接点ごと持ち、課題と進捗を自分で管理する
L5案件全体の設計・推進を担い、依頼元の課題設定に関与する。得た型を他の案件へ渡す
L1 は標準化の外に置く
型を渡しても回せず、個人の書き方で成果物を出す状態。型を渡して回させれば L2 へ上がれるので、育成の出発点が定義で決まる。
L2 は型を理解すれば届く
判定文は型が実際に強制するものだけで書いてある。理解した人が届かないなら、直すのは人ではなく判定文か型の側である。
L5 の行は到達点
5本がすべて真になる人を探すためではなく、どの軸がどれだけ足りないかを言うために使う。
※ 1人の段階は A と B の低いほうで決める。依頼元に対して任せられる部分を A、チームの型の中で任せられる部分を B が測る。
※ 報酬帯との対応は持たない。段階と報酬の結び付け方は各社で違い、評価基準の側に固定すると持ち込めなくなる。

判定文（1/3）　A 上流・提案と関係者調整／B 型の運用

評価者の解釈に委ねる語を使わず、リポジトリの何を開けば真偽が確かめられるかで書く
LvA　上流・提案と関係者調整
L1渡された要件にそのまま着手する。曖昧さは実装が止まる形で表面化する
着手後に要件を問い直した回数
L2着手前に出口と順序を書ける。完了条件が書けないことで、要件の曖昧さが着手前に自分に見える
PLAN.md の出口の節
L3性能・運用・移行の欠落を要件に対して指摘できる。設計を非開発者に読める資料にでき、課題を先出しして進捗を自分で管理する
設計資料、Issue や PR の課題提起
L4持った領域について、依頼元への提案資料と見積の根拠を自分で組める。社内の非開発者と要件を共有し、領域の課題管理と期待値調整ができる
提案資料、見積の内訳
L5案件全体の課題管理と期待値調整を担う。依頼元の課題設定に関与し、提示された要件を組み替えて提案できる。複数案件にまたがる関係を作れる
提案の採否と、要件が組み替わった記録
LvB　標準化されたワークフローの運用
L1型を渡されても回せず、個人の書き方で成果物を出す。詰まったことは聞かれてから報告する
差し戻しレビューの回数
L2指示された手順を回し、標準の形の成果物を出せる。変更1本ごとに区切り、コミットで止まって承認を待てる
PR の粒度、承認の残り方、配られたスキルの使用回数
L3作業に対して回す手順を自分で選べる。他の作業者の成果物を読んで自分の進め方を直せる。型が噛み合わない作業を見分けて手で進める
手順を外した作業と、その理由の記録
L4既存の型の欠落を特定して直せる。無い手順を作る要否を判断し、要ると見れば自分で作ってチームに使わせる
手順の置き場への変更と、自作のスキルが他のメンバーに使われた回数
L5案件横断で型の構成を設計し、他人が回せる形に配布できる。繰り返し起きる詰まりを見つけて型に反映できる
他案件への配布と、配布後の定着

判定文（2/3）　C ドメイン理解／D 検証・品質保証

C は在籍の長さで上がり、段階に連動しない
LvC　ドメイン理解
L1担当した機能の範囲しか知らない。前後の業務フローを聞かれても答えられない
設計時の質問の範囲
L2担当機能の前後の業務フローを説明できる
設計資料の前提の節
L3現行システムの全体構成と、業務上の例外処理の在処を把握している
影響範囲の見積もりの精度
L4依頼元の業務の矛盾や非効率を指摘できる。依頼元と開発者が同じ言葉で話せる状態にできる
用語集、議事の指摘
L5複数案件のドメインを横断し、共通化できる業務の型を示せる
複数案件にまたがる設計
LvD　検証・品質保証
L1動いたことを確認の完了とする
PR の検証手順の節
L2完了条件に「何を読んで確認するか」を書ける。機械で確かめられない変更でも確認手段を言葉にできる
PR の検証手順の節
L3担当領域の公開面に対する保証を列挙し、テストの欠落を指摘できる
docs/guarantees.md とテストの対応
L4案件の非機能要件を検証計画に落とし、リリース判定の基準を決められる
検証計画、リリース判定の記録
L5案件横断で品質基準を定め、他人の検証設計をレビューできる
他案件へ渡した基準

判定文（3/3）　E インフラ・基盤／採点の原則

採点は能力で判定し、5軸を平均しない
LvE　インフラ・基盤
L1用意された環境の上でだけ作業する。手元で動くことと、環境に載ることの区別が付かない
CI の失敗履歴
L2リポジトリの CI 定義とブランチ保護を読み、壊さずに変更を通せる
CI の失敗履歴、force-push の有無
L3担当領域の CI/CD と検証用環境を自分で組める
ワークフロー定義の変更履歴
L4案件のインフラ構成を選定できる。選択をコストと運用性で説明でき、リポジトリ全体の構成を管理できる
構成の選定資料
L5案件横断で基盤の型を作り、他案件へ配布できる
他案件で使われた基盤
採点の原則能力で判定し、実績では判定しない
判定文を成果物の事実だけで当てると、測っているのはやってきたことになる。組めるが組む仕事をしなかった人は、E が実力より低く付く。
  • 軸ごとに L2 から順に真偽を見る。偽になった手前がその軸の点になる
  • 証拠が無い軸は「未観測」として残す。点で埋めない。育成では機会を配れば分かる軸、選考では面接で聞く軸を指す
  • 5軸の平均を取らない。凸凹が消え、次に何をするかが分からなくなる
  • 段階は A と B の低いほうで決める。C・D・E は段階に入れない
採点結果が型の欠陥を指すとき
同じ軸の同じ段階で複数人が同時に止まっているなら、人ではなく型を疑う。ただし型を回して届くのは L2 までで、C は L2 も型では届かない。L3 以上は5軸とも、型を回した経験の副産物では届かない。

各段階の参照ペルソナ

実在の人物を当てず、評価基準の側で固定した架空の人物。実在の人は軸ごとに凸凹するので、全軸が揃った人物は置いていない
Lv ABCDE 人物任せられる範囲
L1 11311 型を渡しても回らず、自分の書き方で書き始める。同じ依頼元を長く見てきたので、C だけが2段高い。 単位作業。着手前にこちらで手順を割ってから渡す
L2 22121 指示された手順を回して標準の形の成果物を出す。入ってから日が浅く、担当機能の前後の業務は答えられない。 単位作業を、完了条件だけ渡してレビュー前提で
L3 33232 中途で入って半年。回す手順を自分で選び、要件の欠落とテストの欠落を指摘する。提案資料や見積はまだ組まない。 担当領域。進め方を渡さず、結果だけ見る
L4 44433 業務側に長く入り、依頼元と開発者が同じ言葉で話せる状態を作る。案件全体のリリース判定までは担わない。 案件の一領域を、依頼元との接点ごと
L5 55454 実装と型の運用から上がってきた人。横断できていないのはドメインと基盤である。 案件全体。依頼元の意思決定層との対話を含む
この5人を設定した理由
段階は、A と B の低いほうに一致させた。規則を当てたとき、迷わず1つの段階に決まる例にするためである。C は段階の順に並べなかった（L1 が3、L2 が1、L3 が2）。在籍の長さが C にだけ関わることを示すためである。L4 の D と E は3にした。段階が同じでも、向く案件がこの2軸で変わることを示すためである。

型を配り、成果物と記録で判定する

評価・育成・採用が同じ成果物と記録を材料にする
循環
型を配る→成果物と記録が出る→現在地を測る→次に伸ばす1軸が決まる→届かない分を採用で埋める
型を配る標準化された手順
手順をチームで回すと、成果物の形が揃う。判定文が根拠にする成果物の置き場は、この型が作る。
成果物を読む1人がどの段階にいるか
リポジトリの成果物に判定文を当て、5軸の点と次に上げる1軸を決める。
利用データを読む型を十分に回しているか
エージェントの利用データから、配られたスキルの使用回数・作業の量・投入の量を見る。B 軸の材料になる。在籍者にだけ当てる。
自社へ持ち込むときに差し替えるもの
判定文の置き場は、使っている型の同じ役割の置き場へ読み替える。置き場が無い役割は判定文ごと落とす。A と C は依頼元が別会社である前提で書いてあるので、自社サービスなら社内の企画・事業側と読み替える。L4・L5 の「案件」は、プロダクト・チーム・組織へ読み替えてよい。段階が表すのは任せられる範囲の広さである。
