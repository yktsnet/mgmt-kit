# board の方針

board で何を決めていて、それはなぜかを書く。方針を変えるときは、この文書を書き換えてから進める。

ladder の5軸で、評価・育成・採用を1つのウェブアプリで回す。評価する担当とマネジメント（非エンジニアを含む）は、
Drive のスプレッドシートを編集するだけでよい。その中身が画面に反映される。

順番がある。**定義を決め、担当を決め、既存の社員を評価する**。育成と採用は、評価が回ってから同じ定義の上で使う。

## 画面

| タブ | 使う人 | やること |
|---|---|---|
| 評価 | Reviewer・Manager | 担当する人について、細目ごとの判定を見て Submit・Approve する。担当ごとの進み具合と、本人ごとの軸の段階・本人の段階を見る |
| 現在地 | 全員 | 評価と評価のあいだに、いまどうかを見て、次に上げる1軸を決める |
| 採用 | Hiring を付けた人・Manager | 同じ定義を候補者に当て、選考の段階を進める |
| 設定 | Manager | 5×5 の定義（細目・Evidence・版）、Reviewer の割り当てと役割、採用枠 |

## 決めたことと理由

### 定義と評価

- **軸は固定、定義は変わる**：A〜E の5軸は動かさない。5軸×5段階の各マスの判定文は運用しながら直すので、版を持たせる。どの評価がどの版で付いたかを残す
- **評価は細目の単位で付ける**：1つのマスには細目が複数ある（例：A の L3 は「欠落を指摘できる」「非開発者に読める資料にできる」「課題を先出しして進捗を管理する」）。細目ごとに判定と根拠を付け、マスは細目がすべて ○ のときに届いたとする
- **段階の決め方は ladder に従う**：board で決め方を作らず、[ladder.md](../../ladder/docs/ladder.md) の決め方をそのまま当てる。細目の判定からの出し方は [sheets.md](sheets.md) の「評価」にある。判定に使える成果物が無い軸は未観測とし、点で埋めない
- **版は、評価か面接が使ったら直せない**：直すときは New version を作る。過去の判定の前提が、あとから変わらないようにする
- **担当は1人に1人**：評価される人1人に Reviewer 1人を割り当てる。自己評価と、複数人のすり合わせは対象外とする

### 置き場

- **設定はアプリが持つ**：Ladder の定義と版、在籍者と Reviewer、役割、採用枠は、アプリの永続する SQLite に置き、設定の画面で直す。Drive には置かない。評価の前提になる値なので、シートと二重に持つとどちらが正しいかで迷う。初版の定義は `ladder/docs/ladder.md` から作り、判定文を句点ごとに細目に分ける。`ladder.md` への書き戻しは対象外とする
- **判定はスプレッドシート、状態と記録はアプリ**：
  - 判定と根拠は、評価される人1人・期1つにつき1ファイルのシートに書く。1行に細目1つで、行は定義の版の L2〜L5 から作る
  - 状態（Draft → Submitted → Approved、Reopen で Draft に戻す）と記録（メモ、状態の切り替え）はアプリが持ち、日時と誰がしたかを残す
  - Submit は判定が途中のうちはできない。Approve は Manager だけができる
  - ファイルの最終の編集日時と編集した人は Drive から取って出す
- **入力は Drive のスプレッドシート**：Drive の `.xlsx` は互換モードや同期の競合が出る。`.xlsx` を GAS で変換すると正本が2つになる。やることは値の入力と簡単な集計なので、Excel にしか無い機能は要らない
- **集計はアプリで行い、変更は更新日時で拾う**：Sheets はファイルシステムの上に無く、監視が効かない。本番の Sheets API とデモの `.xlsx` で同じ作りにする
- **置き場は mgmt-kit の `board/`**：ladder・usage と同じ評価基準を読むので、リポを分けない。アプリは `board/` の下で完結させる

### 採用

- **候補者にも同じ細目を当てる**：在籍者と候補者を同じ尺度で並べるため、面接でも Ladder の細目を判定し、評価と同じ決め方で候補者の軸の段階を出す。面接のシートは評価のシートと同じ形にする。聞く内容は [hiring.md](../../ladder/docs/hiring.md) に従う
- **聞かなかった細目と未観測を分ける**：まだ聞いていないのか、聞いても材料が無かったのかで、次の面接の聞き方が変わる。書き分け方はシートの形（sheets.md の「候補者」）にある。どちらも次の面接で聞くこととして出す
- **選考の段階はアプリが持つ**：評価の状態と同じく、日時と誰がしたかを記録に残す。シートには置かない

### 見せる範囲

- **Manager はすべてを見られる**
- **Member は、Reviewer として担当する人の評価・記録と、Approved になった自分の評価だけを見られる**：自分の評価の記録（Reviewer のメモ）は見せない
- **採用は、設定で Hiring を付けた人と Manager が見られる**：候補者の所見は、在籍者の評価より見せる範囲を狭くする
- **一覧・1人のページ・現在地・API は同じ決まりで絞る**：画面ごとに絞ると、どこかで漏れる
- **タブは、見られるものがある人にだけ出す**：設定は Manager だけが見られ、直せる。担当も採用も無い Member には現在地だけが出る

### Claude Code の利用状況

- **利用状況は現在地に置く**：評価は採点のときしか変わらないが、usage は毎日変わる。評価と評価のあいだのいまどうかを、usage の3つの観点（標準化・作業の量・投入の量）で見る。usage だけで点は付けない。採用には出さない（候補者に利用データが無い）
- **評価のタブでは、B の根拠にスキルの回数を添える**：B の細目のうち、Evidence がスキルの使用回数のものに限り、根拠の欄に usage の数字を並べる
- **Member も全員の平均と比べられる**：現在地の図と表に、全員の1人あたりの平均を出す。図の線は日ごとの揺れが大きいので、5日平均にする。平均は3人以上のときだけ出す。2人だと、平均と自分の値から相手の値が割り出せる
- **usage は MD ではなく JSON を読む**：`usage/tools/usage/claude-code/data/` の日ごとの JSON を直接読む。人の突き合わせはメールで行い、ログイン・シート・usage で同じ鍵を使う

### 作り

- **ログイン**：Sign in with Google で、許可した Google Workspace のドメインだけを通す（ID トークンの `hd` で判定する）。ドメインの人は誰でも入れ、初めて入ったときに Member として在籍者に載る。在籍者を手で足す手間をなくし、誰が入れるかは Workspace の側で決める。環境変数 `BOARD_MANAGERS` に書いた人は、入ったときに Manager になる。Reviewer の割り当てと Hiring は Manager が設定の画面で決める。デモでは Google を通らないログインを使い、在籍者ごとに見られるものを並べる。アプリが Drive を読む権限は、ログインとは分けてサービスアカウントに持たせる
- **フロントエンドのビルドを持たない**：FastAPI と HTML で作る
- **画面の言葉**：日本語で言い回しが硬くなるところは英語にする（Evidence、New version など）

## 対象外

GA4、求人媒体からの取り込み、GAS、自己評価、複数人のすり合わせ、`ladder.md` への書き戻し。
